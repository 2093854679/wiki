# V1 与 V2 固件体积对比

## 结论概览

| 项目 | V1 (xiaozhi-esp32-main) | V2 (xiaozhi-esp32-main-v2) |
|------|-------------------------|-----------------------------|
| **app 固件典型大小** | 较小（具体视构建而定） | **约 6.5 MB**（0x677160，desktop-pet） |
| **原因** | 显示/板级/依赖更精简 | 多出 LVGL 显示层、更多板级公共代码、更多依赖与字体 |

---

## 一、为什么 V2 固件更大？

### 1. 主程序多出一整块「LVGL 显示层」（主要增量）

V2 在 `main` 里显式编译了 LVGL 相关显示与资源逻辑，V1 没有这些**统一进 app** 的显示层：

| V2 多出的源码（进 app） | 说明 |
|-------------------------|------|
| `display/lvgl_display/lvgl_display.cc` | LVGL 显示封装 |
| `display/emote_display.cc` | 表情/形象显示 |
| `display/lvgl_display/emoji_collection.cc` | Emoji 集合 |
| `display/lvgl_display/lvgl_theme.cc` | 主题 |
| `display/lvgl_display/lvgl_font.cc` | 字体封装 |
| `display/lvgl_display/lvgl_image.cc` | 图片 |
| `display/lvgl_display/gif/lvgl_gif.cc` + `gifdec.c` | GIF 解码 |
| `display/lvgl_display/jpg/image_to_jpeg.cpp` + `jpeg_to_image.c` | JPEG 编解码 |
| `assets.cc` | 内置资源管理 |

V1 只有：`display/display.cc`、`lcd_display.cc`、`oled_display.cc`，没有上述 LVGL/emoji/GIF/JPEG 这一整套。

---

### 2. 板级公共代码更多（boards/common）

V2 的 `CMakeLists.txt` 里**显式**加入了一长串板级公共源文件，V1 只是 `file(GLOB ... boards/common/*.cc)`，实际包含的文件更少。

V2 多出或更完整的包括例如：

- `board.cc`、`wifi_board.cc`
- `ml307_board.cc`、`nt26_board.cc`、`dual_network_board.cc`
- `adc_battery_monitor.cc`、`afsk_demod.cc`、`axp2101.cc`
- `backlight.cc`、`button.cc`、`i2c_device.cc`、`knob.cc`
- `power_save_timer.cc`、`press_to_talk_mcp_tool.cc`、`sleep_timer.cc`、`sy6970.cc`、`system_reset.cc`
- `esp_video.cc`（S3/P4）、`esp32_camera.cc`（S3）

这些都会增加 app 体积（即使用不到，若被链接进去也会占空间）。

---

### 3. 状态机 vs 事件

- V1：`device_state_event.cc`（事件驱动，逻辑相对简单）
- V2：`device_state_machine.cc`（状态机，分支和状态更多）

状态机实现通常比简单事件处理代码量更大，也会带来一定体积增加。

---

### 4. 依赖组件更多、更新（idf_component.yml）

| 类别 | V1 | V2 |
|------|----|----|
| **音频** | esp_codec_dev, esp-sr | 同上 + **esp_audio_effects**、**esp_audio_codec** |
| **网络/模组** | esp-ml307 | 同上 + **uart-eth-modem**、**78/esp-ml307** 更新 |
| **显示/图像** | lvgl, image_player, esp_emote_gfx | 同上 + **esp_image_effects**、**esp_new_jpeg**、**esp_video**（S3/P4） |
| **字体** | xiaozhi-fonts ~1.4.0 | **xiaozhi-fonts ~1.5.5**（字体更多或更完整） |
| **LVGL** | lvgl ~9.2.2 | **lvgl ~9.3.0** |
| **ESP-SR** | esp-sr ==2.1.4 | **esp-sr ~2.2.0** |
| **其他** | — | **esp_mmap_assets**、**otto-emoji-gif-component**（S3）等 |

更多、更新的组件会带来更多被链接的库和代码，从而增大固件。

---

### 5. 链接的 ESP-IDF 组件更多（PRIV_REQUIRES）

V2 的 `idf_component_register` 里显式写了较多 `PRIV_REQUIRES`，例如：

- fatfs, esp_pm, esp_psram  
- esp_driver_jpeg, esp_driver_ppa  
- esp_app_format, app_update, spi_flash, console, efuse, bt  

V1 没有这一长串，默认链接的组件更少，固件更小。

---

### 6. 内置资源（EMBED_FILES）与字体

- **语音 ogg**：V1 和 V2 都用 `EMBED_FILES ${LANG_SOUNDS} ${COMMON_SOUNDS}`，把当前语言的 ogg 打进 app，这部分两边都有，不是 V2 独有的增量。
- **字体**：V2 通过 **xiaozhi-fonts** 和 **BUILTIN_TEXT_FONT / BUILTIN_ICON_FONT** 把选中的字体打进默认 assets 或参与构建；V2 字体版本更高、选项更多，若部分字体数据被链进 app 或默认 assets 更大，也会推高「固件 + 默认资源」总体积。

---

### 7. desktop-pet（原 startnorva）板子本身

- V1：startnorva 只有 `boards/startnorva/ui/*` + 板级 common，没有 V2 那套 LVGL 显示层和那么多 common。
- V2：desktop-pet 在**已有**的 LVGL + 更多 common 之上，再叠一层 CJ_display + EEZ UI，相当于「更大底座 + 同一块板子 UI」，所以同板子下 V2 固件会明显大于 V1。

---

## 二、对比小结

| 因素 | 对体积的影响 |
|------|--------------|
| LVGL 显示层（emoji/GIF/JPEG/主题/字体/资源管理） | **大**，V2 独有 |
| boards/common 显式加入大量板级代码 | **中~大** |
| device_state_machine vs device_state_event | **中** |
| 更多、更新的依赖组件（音频/图像/字体/LVGL/ESP-SR） | **中~大** |
| PRIV_REQUIRES 引入更多 IDF 组件 | **中** |
| 内置 ogg | 两边都有，不是 V2 独有增量 |
| desktop-pet 板子 UI | 在更大底座上再叠一层，整体更大 |

整体上，V2 固件更大主要是因为：**在保留板子 UI（如 desktop-pet）的前提下，引入了统一的 LVGL 显示框架、更多板级支持、更多依赖和字体**，功能更多、适配板型更多，体积就会比 V1 大。若需要缩小 V2 固件，需要从「裁剪 LVGL 显示层、裁剪 boards/common、精简依赖和字体」等方面做针对性裁剪。

---

## 三、如何自己对比一次体积

在各自工程目录下执行（先选同一块板子，如 desktop-pet / startnorva）：

```bash
# V1
cd xiaozhi-esp32-main
. ~/esp32/esp-idf/export.sh
idf.py set-target esp32s3   # 并选 startnorva
idf.py build
idf.py size

# V2
cd xiaozhi-esp32-main-v2/xiaozhi-esp32
idf.py set-target esp32s3   # 并选 desktop-pet
idf.py build
idf.py size
```

用 `idf.py size-components` 可看各组件占 Flash/RAM，便于定位哪些模块最占空间。
