# LLM Knowledge Base — Codex Integration

This vault is an LLM-powered knowledge base. Raw source documents live in `raw/`,
the compiled wiki lives in `wiki/`. Everything is managed via the `kb` CLI.

## Key directories

- `raw/` — Source documents (articles, papers, repos, datasets, images). You read these but rarely edit them.
- `wiki/summaries/` — Per-document summaries for **high-value** raw files only.
- `wiki/concepts/` — Cross-cutting concept articles synthesized from multiple raw documents.
- `wiki/categories/` — Category hub pages auto-generated by `kb index`.
- `wiki/categories/bk-doc/` — Per-chip hub pages with full module navigation to raw files.
- `wiki/outputs/` — Generated outputs: Q&A answers, Marp slides, matplotlib charts.
- `wiki/index.md` — Master index auto-generated by `kb index`.

## Tiered strategy — NOT every raw file needs a summary

Raw files fall into three tiers:

| Tier | What | Action |
|------|------|--------|
| **1. API reference** | `bk_uart.md`, `bk_gpio.md` 等函数签名文档 | 不写摘要。芯片 hub 页已有导航链接，读 raw 原文即可 |
| **2. Overview / Guide** | `bk_overview.md`, `bk_wifi.md` 等架构级文档 | 写摘要。这些是高频入口，TLDR 有价值 |
| **3. Cross-cutting concepts** | 跨多篇 raw 才能理解的主题 | 写 concept。如安全体系、WiFi 架构、OTA 流程 |

## Auto-ingest rule (CRITICAL)

**Every time this conversation starts, or the user says "处理一下" / "有新内容" / "更新wiki" / "编译"**
you MUST execute this exact sequence:

1. `python -m tools.kb ingest --status new` — check only genuinely new files
2. If new markdown files exist: assess each against the tier table above
   - Tier 1 (API ref): ensure linked from the appropriate chip hub page, then `python -m tools.kb update-manifest <path> <hash>`
   - Tier 2 (overview/guide): read, write summary to `wiki/summaries/`, update manifest
   - Tier 3 (cross-cutting): extract concepts to `wiki/concepts/`
3. If new module directories appear in raw: update the chip hub page navigation
4. `python -m tools.kb index` — rebuild index
5. `python -m tools.kb stats` — confirm

Never wait for the user to ask twice. The raw/ directory is the trigger — new content there means
the wiki needs updating. You are the LLM compiler, so do the compilation directly
(do NOT call `python -m tools.kb compile` — that requires an external API key; you ARE the LLM).

## Common workflows

### Answering a question against the wiki

Start with local evidence retrieval. Run commands from the repository root;
from `wiki/`, use `python ../kb.py` instead of `python -m tools.kb`.
The wrapper `python <absolute-repository-path>/kb.py` works from any directory.

1. Run `python kb.py context "<question>" --json-output` for a bounded evidence pack.
2. For BK questions, supply the known `--chip`, `--family`, `--version`, and
   `--processor AP|CP` filters. `--chip` can repeat for comparisons. Inspect
   `applied_filters` and each result's `matching_scopes`; never substitute another
   chip, SDK version, or processor when evidence is missing.
3. For exact functions, use `search "bk_uart_init" --chip BK7236 --kind api
   --json-output`. Verify signatures, return values, and constraints with
   `read "<workspace_path>" --start-line N --end-line M --json-output`.
4. Cite the original file and line range; retain `source_url` for official links.
   Overview questions can use summaries/concepts; API details require raw text.
5. An empty result means insufficient evidence. Try a module name or Chinese /
   English alias within the same scope. Do not answer from unrelated defaults.
6. Search is local and needs no LLM key. `query` calls the configured external
   LLM; prefer `context` when you are already the answering AI.

Navigation fallback: `wiki/index.md` → `wiki/categories/beken-official.md` or
`wiki/categories/bk-doc.md` → chip/module → raw. See `wiki/AI-SEARCH.md`.
Default retrieval excludes historical-unverified mirrors and outputs; opt in
with `--include-historical` or `--kind output` when explicitly relevant.

### Health check / Linting
Run `python -m tools.kb lint --check consistency|gaps|suggestions` to find:
- Inconsistent data across articles
- Missing topics or data gaps
- Interesting cross-connections for new articles

### Enhancing the wiki
When you answer a question or discover something new, file the output back into the wiki:
- Good Q&A answers → `wiki/outputs/` (then optionally promote to `wiki/concepts/`)
- New cross-cutting insights → Write a new concept article in `wiki/concepts/`
- Cross-links discovered → Update `[[wikilinks]]` in relevant articles

## Wiki Conventions
- Use `[[wikilinks]]` for internal links (Obsidian format)
- Concept articles should have a `## Related` section with backlinks
- Summaries should use `> **Source:** [text](path)` format (not `[[wikilinks]]`) for indexer compatibility
- Every concept article needs a brief TLDR at the top

## Templates
Jinja2 templates in `tools/kb/templates/` define the structure for generated content.
Use `python -m tools.kb render` to apply a template to data.
