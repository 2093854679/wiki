# Wiki 对 LLM 的使用体验评估

> **TLDR:** 保留 raw → 高价值摘要 → 跨文档概念的分层。优先修复原文链接、芯片范围和增量状态；精简重复入口与每次聊天的维护动作。继续堆摘要的收益低于这些修复。

2026-10-21 检查了本地目录、维护 CLI、索引模板、链接、manifest 和搜索结果，并抽读部分文章。文章技术内容为抽样检查，未逐篇核验。以下为新增本报告前的快照：

- raw 有 1,834 篇 Markdown、5,465 个文件。
- 补充检查发现 50 处指向不存在本地路径的普通 Markdown 链接，按链接出现次数计。其中分类页 42 处、摘要 7 处、概念 1 处；43 处涉及缺失的 BK7236 目录。
- manifest 有 3,838 条记录：1,986 个现存文件未登记，359 条记录对应的文件已不存在，已登记且仍存在的文件无 hash 变化。未登记文件包括 689 篇 Markdown、424 张图片和 873 个未识别类型文件。

## 1. 先修复证据链，再扩充内容

`raw/beken/bk_idk/BK7236/` 当前不存在，但 [BK7236 hub](../categories/bk-doc/bk7236.md) 及 WiFi、安全、OTA、低功耗摘要还在引用它。摘要可以读到结论，核对原文时却会中断。

另外，BK7236N 的 USB、BK7258 的 WiFi/netif 入口，以及两篇学习笔记的 Source 路径也存在失效项。

建议：确认资料是删除、迁移还是尚未恢复；有明确对应关系时再修路径。无法恢复的来源应明确标注缺失，并降低相关结论的可信状态。不要把 BK7236 来源直接替换成 BK7236N 或 BK7258。

验收：所有分类页、Source 链接及概念内的本地 Markdown 链接都能访问；缺失来源有清晰标记。

## 2. 用范围筛选保护检索结果

当前搜索是全文检索加 BM25 排序，CLI 没有芯片、SDK 文档族或 AP/CP 筛选。实测 `BK7236 UART` 的第一条结果是 `raw/beken/bk_idk/BK7258/projects/examples/peripherals/uart.md`；它命中了正文中的关键词，不能据此当作 BK7236 资料。

SMP AP、CP 两份 UART API 的自动元数据均得到空的 `chip`，`module` 则被推断为 `bk_avdk_smp`，也没有独立的处理器侧字段。同名 API 需要更明确的范围。

建议优先补充 `chip`、`sdk_family`、`processor`、`module` 和可确认的版本信息，提供对应筛选。范围未知时标为未知。API 问题定位后直接读目标 raw；解释类问题优先读概念。无需固定逐层打开五个导航页。

验收：目标芯片不存在资料时明确返回缺失；AP/CP UART 查询分别定位到对应侧的 API 与示例。

## 3. 总入口只承担路由，减少重复 TLDR

[总索引](../index.md) 检查时约 5,413 字符，[语义地图](../concepts/concept-map.md) 约 2,234 字符。总索引的 8 个 Core Concepts 又在 Concepts 全表中重复出现；这一重复区段约 1,342 字符。

建议把总索引收敛为按问题分组的短路由：BK/SDK、C/MCU、RTOS、通信、项目。每项只保留一句用途和链接。完整概念列表下沉到独立目录，或与语义地图合并职责。长 TLDR 留在文章正文，不在多个索引反复复制。

Study Note 按原始文件夹分组，导致 WiFi、BLE、FreeRTOS 聚在“职业发展”；这可以保留为来源视图，但不适合充当唯一的主题导航。Desktop Pet 的多个单条文件名分组也可以合并为显示、通信、交互、开发环境。

修改应落在 `tools/kb/templates/index.md.j2` 和 indexer 生成逻辑中，否则手工改总索引会被下次生成覆盖。

## 4. 将聊天启动检查与编译分开

当前聊天工作目录是 `D:/Desktop/obsidian/wiki`，而 `python -m tools.kb ...` 需要在 `D:/Desktop/obsidian` 运行。在当前目录原样执行会出现 `No module named tools`。配置虽从仓库位置加载，其中相对路径仍按进程工作目录解释。

“每次聊天必须 ingest、处理、index、stats”也会使一次知识问答或结构评估被大批未登记文件牵走。本次 ingest 默认输出约两千行，且扫描会计算所有文件 hash。`index` 还会全量重建 raw 与 wiki 的搜索库。

建议：

- CLI 自行确定仓库根目录并解析所有路径，允许从 wiki 子目录运行。
- 聊天启动只做简短、只读的状态检查；用户要求更新或确认有变动时再编译。
- 状态命令默认显示数量和小样本，用显式参数展开明细。
- 区分新建、变更、删除和迁移。只查 `--status new` 会漏掉原文件修改及删除。
- 已经有 `kb refresh`，可以将其完善成单一维护入口，但应明确它目前只扫描、重建索引和报健康状态，并不会替 LLM 完成内容编译。

本次保留了未登记项与 stale 记录，没有用 bootstrap 将所有文件直接标记为已编译。完整 ingest 仍需确认高价值指南的摘要覆盖和旧路径迁移关系。

## 5. 补充适用边界，防止摘要把局部结论泛化

58 篇摘要目前均无 YAML frontmatter，20 篇概念中 11 篇有 frontmatter。现有元数据主要是类型和别名，缺少统一的适用平台、来源版本及核验状态。

建议保持轻量：摘要记录来源、适用范围及核验状态；概念说明通用规律与特定项目经验各自的边界。来源继续保留可点击的 `> **Source:**` 格式，避免破坏现有索引器兼容。

抽查发现 [ARM Cortex-M 基础](../concepts/arm-cortex-m-embedded-fundamentals.md) 将 CPSR/SPSR、User/FIQ/IRQ 等模型写入 Cortex-M 主题。Cortex-M 的 xPSR、Thread/Handler 与 MSP/PSP 模型应单独讲清，可对照 [Arm 官方 CMSIS 核心寄存器文档](https://arm-software.github.io/CMSIS_5/Core/html/group__Core__Register__gr.html)。这类范围混合会被总索引 TLDR 再次传播，值得优先人工核对。

[物联网通信协议全景](../concepts/iot-communication-protocols.md) 的 MCP 统一应用层表述也应明确限定为相关项目的设计选择，避免把项目架构写成所有 IoT 系统的统一要求。

## 6. 保留资料路径，在检索与工具层精简

不建议为了减少文件数就合并所有原始芯片文档。相同内容在不同芯片路径下仍承担来源和导航作用。可以按 hash 合并展示重复搜索结果，同时保留芯片与文档族标签。

`graph-health` 当前只扫描非生成文章的 wikilinks，没有检查分类页和普通 Markdown 链接，因此没有报出上述 50 处失效路径。它还把代码示例中的 `[[wikilinks]]` 当作未解析链接。建议补本地链接、来源、锚点、同名歧义和元数据检查，并跳过代码内容。

`kb lint` 当前会调用外部 Anthropic API，默认按路径排序取前 30 篇、每篇截取前 5,000 字符；它不是完整的本地健康检查。建议将确定性的文件检查放在本地，把语义矛盾检查留给当前对话或显式启用的外部 LLM。

## 建议实施顺序

1. 恢复或标记缺失来源，修正 50 处本地链接。
2. 修复目录无关运行、manifest 迁移与本地健康检查。
3. 加上芯片、SDK 文档族、AP/CP 的范围筛选。
4. 收短总索引，合并重复路由职责。
5. 核对高风险技术概念，再按实际问题补少量高价值摘要。
